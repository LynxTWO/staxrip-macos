# Semantic appearance evidence

Slice 034 under D-061 / R-043 is approved for build, not yet accepted.

The original fixed teal has sRGB contrast 2.396:1 on white and 2.049:1 on a 0.93 neutral surface; on a 0.12 dark surface it has 6.912:1. This makes one constant unsuitable for small active text in both appearances. Candidate reference colors and tint math were evaluated before implementation.

[W3C contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) informs the 4.5:1 small-text design benchmark; this is not a whole native-app conformance claim. [Apple's dynamic color provider](https://developer.apple.com/documentation/appkit/nscolor/init(name:dynamicprovider:)) resolves a color using the supplied drawing appearance. [Apple's increased-contrast appearance guidance](https://developer.apple.com/documentation/appkit/nsappearance/name-swift.struct/accessibilityhighcontrastdarkaqua) says AppKit derives that appearance from the user's setting; the app must not force it on views. Reference tests may resolve it directly without changing system preferences.

Need: readable app-owned text and action labels. Authority: owner design delegation, D-061 / R-043. Worst case: faint status or action text makes correction difficult; consequence is presentation only, with action guards and encoding untouched. The simplest change is one shared dynamic palette and a shared native prominent modifier, not a new theme subsystem. No runtime telemetry or media processing is added. Existing primary/secondary system labels and chart-series colors keep their separate meanings.

The initial candidate compiled but failed 57 contrast assertions. A standalone AppKit probe showed that on this development OS, constructing either increased-contrast appearance while the system setting is off returns the corresponding ordinary appearance, including inside the dynamic provider. The revised palette therefore meets the 7:1 reference target in the base appearances too, using deep teal/amber on light surfaces and pale teal/amber on dark surfaces. There is no separate untested high-contrast-only branch. The unchanged requested-appearance checks passed, then the normal-appearance threshold was strengthened from 4.5 to 7 as well. This does not claim a native walkthrough with the owner's Increase Contrast setting enabled.

The old palette counterexample and four requested-appearance cases initially passed after that revision in 0.023 seconds. Actual resolved window/control colors and neutral references include zero through 12 percent same-color tint. White primary labels and the custom queue shortcut at 85 percent opacity are checked separately. The chart's original series colors are held fixed; only its source-verification status label adopts warning semantics. Action closures, guards and keyboard shortcuts are unchanged. Native rendering and full regression remain pending.

The optimized build at fcc1a76 passed in 16.22 seconds. Native workspace light/dark navigation, recipe and custom Add to queue showed the intended deep/pale accents and readable white filled label. Command-J added one demo configuration and the existing duplicate-name guard disabled another add. A generated existing-output queue check displayed its warning count, badge and remedy in both appearances without writing output. Edit dismissed with Escape, and Return saved the unchanged configuration through the native default action. Inspection also found that segmented controls can draw a white selected label on the inherited bright tint. All existing segmented pickers now explicitly use the separate deep fill, with native selected/inactive text behavior retained; this refinement requires a fresh native check and final regression.

The first full local run at fcc1a76 passed 244 tests / 55 suites in 205.220 seconds, including the strengthened 7:1 base-appearance checks. The generated inputs and prior journal remained unchanged after the read-only native appearance walkthrough. A new build and regression will qualify the segmented-fill refinement.
