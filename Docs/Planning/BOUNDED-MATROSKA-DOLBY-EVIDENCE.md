# Bounded Matroska Dolby packet reader evidence
Version: 0.1. Date: 2026-10-03. D-094 / R-059 / Slice 049.
Status: generated and complete private-source checks passed. Development-only; no native/runtime conversion admission.

## Contract

`Tools/DolbyMetadataAudit` adds `mkv-json` protocol 2, retaining every original HEVC packet and RPU in input order. One unambiguous video track, finite clusters, hvcC length-prefix framing and selected-video unlaced SimpleBlock/BlockGroup are supported. Track/configuration/raster/crop/display-unit declarations remain distinct from decoded picture measurements. Signed relative timestamps are retained as checked nanosecond PTS. Explicit BlockDuration remains optional; DefaultDuration is reported separately and is not falsely substituted for a missing explicit duration. NAL type 63 counts are encoded enhancement declarations, not enhancement pictures or reconstructed residuals.

The scanner consumes/hashes all bytes, including skipped audio/subtitles/metadata, before independently rescanning the whole source and checking descriptor/path identity and size/mtime/ctime. Malformed headers/parent boundaries, partial packets/RPUs and explicit read/output errors cannot complete. Original-file stability is checked at boundaries, not an immutable snapshot. Complete plus successful exit are both required. No helper file writes, media encoding, native packaging, new crate, owner queue execution, source/journal edits or archive publication.

Reject unsupported timing/packet interpretation: selected content compression/encryption, nonzero codec delay/track offset, non-unit TrackTimestampScale, TrackOperation, codec-state changes, additional block payloads and video lacing. Multiple video tracks, other codecs/containers, unknown-size clusters, concatenated documents and Info/Tracks after clusters also refuse. Unknown finite irrelevant elements are consumed within parent bounds; this is not complete Matroska/EBML-CRC, parameter-set/slice/POC or decoder conformance validation. A structurally complete valid shorter unknown-size segment still needs an expected sequence to detect omitted suffix media.

Limits: 1 TiB file; 16 MiB selected packet; 1 MiB per track configuration; 256 tracks; 128 million parsed elements; 32 million encountered blocks; two million selected packets/RPUs; 64 KiB escaped RPU; 2 MiB JSON record; 64 MiB tracked Rust heap. Stack/allocator overhead/code pages/OS memory are outside that heap claim. Core dumps remain disabled. Regular nonempty local files only. Library parsing/CRC comes from the unchanged pinned MIT libdovi; no independent Dolby reference renderer is claimed.

## Complete private source evidence

Initial complete source execution passed, consuming the entire 56,475,108,340-byte source plus its independent recheck in 286.654 seconds. All 120,552 video packets matched the prior complete independent FFprobe payload size/hash and PTS reference; configuration bytes/hash and whole-source SHA-256 matched prior evidence. Every RPU's full dictionary and wire digest matched the original complete archive after independently checked unique-PTS presentation ordering. Every packet has exactly one RPU in this particular source; all 120,552 classify as Profile 7 MEL. There are 1,372 declared scene refreshes, one unique declared active area and 1,371,271 type 63 NAL declarations. These are metadata/NAL observations, not measured scene brightness, active black-pixel bounds or enhancement-picture counts. Tracked peak heap was 3,132,901 bytes under the existing 67,108,864-byte ceiling; this is not a total RSS benchmark or throughput guarantee.

At ordinal 46, an apparent mismatch was actually the first differing RPU across a presentation reorder. Pinned dovi_tool 2.3.4 `general_read_write.rs` explicitly sorts its extracted RPU archive by parsed picture order count before writing. Our reader preserves original packet order. Under this source's checked unique PTS and one-RPU-per-packet conditions, sorting reference associations by source PTS yields complete metadata/wire agreement. Keep both original packet ordinal and timestamp in future manifests. This does not implement a generic POC decoder or certify one RPU per displayed/decoded picture for other sources, duplicate timestamps, preroll, invisible pictures or timing edits.

## Primary definitions and separate hosted status

The [Matroska specification notes](https://www.matroska.org/technical/notes.html) define signed block timestamps and lacing. The [element specification](https://www.matroska.org/technical/elements.html) defines timing, crop and display-unit semantics. [RFC 8794](https://www.rfc-editor.org/rfc/rfc8794) defines EBML framing. The evaluated [matroska-demuxer 0.8.1 source](https://github.com/hasenbanck/matroska-demuxer/blob/v0.8.1/src/lib.rs) returns false on some I/O errors in next_frame; it was not added as a dependency. [Pinned dovi_tool extraction](https://github.com/quietvoid/dovi_tool/blob/614c816b6446dcd1dbaf433403d499a6026fbb5a/src/dovi/general_read_write.rs) explains display-order archives. The independent reference's [FFmpeg Matroska reader](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/matroskadec.c) rejects DocTypeReadVersion above 3 in the evaluated version.
