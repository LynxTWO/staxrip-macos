# Chapter metadata operation queues

D191 implements the owner-approved queue change in the existing batch metadata write consumer. Each write uses a fresh serial DispatchQueue at utility QoS with the default target. The same exclusive Data.write, continuation, error handling and post-write cancellation check remain. A submitted operation is awaited before returning or releasing staging; cancellation does not bypass a queued or active write. No shared queue, priority escalation, global concurrency limit or decoder test-budget change.

PR154's retained evidence placed AV1 and TenBit submission records before their 120-second issues and worker/write-return records afterward. This is the motivation for a bounded repair trial, not proof of queue starvation or the cause of all 21 timeout issues. Existing time limits and assertions remain unchanged.

A DEBUG queue preparation hook lets generated tests enqueue a blocker before the actual write. Three new tests exercise cancellation before the initial cancellation check, behind that blocker, at worker entry and after write return; collision/error precedence; missing-parent failure; and a second independent write completing while the first queue is held. Existing success/collision/nil-metadata and generated MKV/MP4 batch tests remain. Held-worker tests do not interrupt Data.write inside an OS call. Queue identity and one observed independent completion do not guarantee scheduling latency.

The test caller always releases its gate and awaits the exact operation before removing its generated directory. Review found a potentially throwing observation before release; the final test saves that error, releases and joins, then rethrows while retaining the root. This was a source-review correction, not an observed runtime failure. A gate escape records failure and retains its roots. No new uncertain-resource cleanup authority is introduced.
