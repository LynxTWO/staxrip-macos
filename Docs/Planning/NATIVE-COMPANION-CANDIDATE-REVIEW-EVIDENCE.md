## Contract and authority

After a coordinator disappears, its transient component receipt is unavailable. A valid
surviving stage or published result must be examinable against the original source using
only its fixed files. The owner delegated this generated non-audio prerequisite. No
archive action, recovery adoption/deletion/republication, directory search, importer,
source media processing, signing retry, merge or release is authorized by these findings.

`CompanionDiskCheck.reviewOriginalCandidate` takes explicit source, candidate directory,
retention and fixed trusted metadata reader. It shares the existing dedicated pinned
native disk worker with receipt-based verification. It does not take a lost coordinator
receipt, test acknowledgment or manifest-selected source path/executable.

## Concrete admission

Source and candidate descriptors are opened with no-follow flags. The candidate must be
owned private0700 with fixed retention-specific membership. Each fixed component is an
owned regular0600 single-link file within its existing bound. Original source bytes/hash,
candidate ID and component bytes/hashes are observed from the pinned files. Whole-container
mode also compares every byte directly to the pinned source. No stored digest alone
establishes truth. Manifest is itself hashed from disk; its self-hash is not persisted.

Only three bounded unsigned count claims are bootstrapped from fixed manifest.json using
D111's strict native JSON grammar. These claims are not admitted counts. D109-D114 then
require original TrackEntry/hvcC, independently reconstructed signed duplicate-preserving
packet order/raw escaped RPUs, index, full exact manifest schema/component/hash/retention/
qualification/offset relationships, native audit/container declarations and actual owned
fresh libdovi metadata equal the stored audit. Counts must equal original source traversal.
Every source/candidate/member final path/descriptor observation must still match before
return. A successfully returned receipt is current source-dependent semantic review only.

Receipt-based APIs remain narrower where previously narrower. Their supplied source/
stage/member observations must still agree with reread disk facts; malformed supplied
lengths refuse before component hashing. Both inputs share one read worker and pinned
capabilities. There is no second filesystem scanner or Python runtime adapter.

Configured existing limits remain: source/full-container1TiB, track/config/manifest1MiB,
raw/index512MiB, audit1GiB, bounded1MiB source/component reads, two million packets/RPUs,
existing bounded audit/index row/line limits and owned reader120-second max. These are
configured bounds, not peak-memory measurements or physical I/O preemption guarantees.

## Limits

The existing finite Matroska/HEVC source reader is reused; this adds no MP4/AV1 source
parser or broader container support. Version zero remains a source-dependent prototype. It is not a portable or stable
importer, immutable snapshot, persisted producer execution binding, independent libdovi
implementation, interpretation of every raw RPU field, decoded picture association or
edited geometry conversion. A candidate can match source without proving who produced it,
whether it was exclusively committed, or whether its data survived power loss.

The native API is unused by the app. It opens read capabilities but does not acquire
production security-scope leases or install recovery UI. Release helper provenance,
packaging, retained review release/recovery and actual sandbox grant/revocation remain
gates. Ordinary read-only return closes descriptors/settles its worker and helper; typed
unsettled ownership must preserve review in any future controller. No archive path or
receipt is cleanup/adoption/access-release authority.

Metadata-only excludes BL/EL pictures and outside-track information and retains selected
embedded names/metadata. Whole-container retains the entire source including all streams/
names/metadata with source-sized storage/privacy. Owner losses/storage/privacy review is
still required before an action. Preservation, compatible conversion, edited-picture
statistics, enhancement reconstruction and archival remain separate qualified workflows.
